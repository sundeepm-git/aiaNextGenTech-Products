# Prerequisites

Complete following steps if not completed
- The exported code must be checked into the `GitHub` export repository under the `Export` folder.
- The latest exported code must also be available locally in the `azure-export` directory.


Before proceeding with the environment setup, ensure you have the following prerequisites:

- `Python 3.8` or higher installed on your system
- pip (Python package manager)
- Git (for cloning the repository, if not already done)

# Environment Setup


To set up your Python environment and install all dependencies for the Code Refactor Engine, follow these steps:

1. Open a terminal and navigate to the `python` folder in your project:
  ```sh
  cd python
  ```

2. (Optional but recommended) Create and activate a virtual environment:
  ```sh
  python -m venv .venv
  source .venv/bin/activate   # On Linux/macOS
  .venv\Scripts\activate     # On Windows
  ```

3. Install all required dependencies from `requirements.txt`:
  ```sh
  pip install -r requirements.txt
  ```

# How to Run Code Refactor Engine

To run the Code Refactor Engine, use the following command from the `python` directory:

```sh
python refactor.py "<Subscription Folder Name>" "<Subscription ID>" "<Resource Group Name>"
```

Example:
```sh
python refactor.py "Azure Tower Subscription" "4947a0ea-fdf3-4665-858f-09edba89fc5f" "rg-cis-scus-01"
```

<b style="color:#800000;">When you run the engine, you will see the following warning prompt:</b>

---
**WARNING – Refactor Engine Execution Notice**

If this is your first execution of the refactor engine for the following scope, the tool will generate and refactor all resources:

Subscription: Azure Tower Subscription  
Resource Group: rg-cis-scus-01

If you run the refactor engine a second time or more against the same Resource Group, all previously refactored files and changes will be overwritten.

⚠️ **Important:** This tool is intended to be executed only once per Resource Group. Re-running it on the same Resource Group will replace existing refactored output.

Please choose an option:
- **Yes** – Proceed to refactor and overwrite any existing refactored files
- **No** – Cancel the operation and keep the existing refactored files unchanged
---

# Validate Code Refactor Output

After running the engine, validate the output in the following directory:

```
az-tf-refactored/<Subscription Name>/<Resource Group Name>
```

Check that the following files are created:

- **main.tf**: Contains the Terraform resource definitions for your Azure infrastructure, refactored from the export.
- **terraform.tfstate**: The Terraform state file that tracks the current state of your infrastructure. This file is created during the export process.
- **variables.tf**: Autogenerated. Defines all input variables used in your Terraform configuration using the main.tf and can be updated during manual review and refactor, including those extracted from Azure resources and marked as sensitive where appropriate.
- **terraform.tfvars**: Autogenerated. Provides values for the variables defined in `variables.tf` and reads the values from `main.tf`. This file is used to customize your deployment for different environments or resource groups.
- **backend.tf**: Defines the remote backend configuration (e.g., Terraform Cloud) for storing the Terraform state file securely and centrally. (Create Manually during STEP 4)
- **locals.tf (optional)**: Standard Terraform file for defining local values and expressions to simplify and reuse logic in your configuration. This file is currently not in use but will be leveraged in future enhancements.

  Example:
  ```hcl
  locals {
    resource_prefix = "aztf"
    location_short = "scus"
  }
  ```
  In this example, `resource_prefix` and `location_short` are local values that can be referenced throughout your Terraform configuration to maintain consistency and reduce repetition. For instance, you might use `local.resource_prefix` when naming resources or `local.location_short` to standardize region codes.

- **outputs.tf**: Standard Terraform file for defining output values that are returned after applying your configuration, useful for sharing data between modules or with external systems. This file is currently not in use but will be leveraged in future enhancements.

  Example:
  ```hcl
  output "vm_name" {
    value = azurerm_linux_virtual_machine.azvm_3.name
  }
  ```

Ensure all these files are present to confirm a successful refactor and export process.

# Code Refactoring Rules

## STEP 1 Variables.tf Handeling

### Type Of Exported Variables 

| Field Name         | Field Type | Description                                   | How to Handle                                      |
|--------------------|------------|-----------------------------------------------|----------------------------------------------------|
| id, *_id, *_ids    | string/list| Resource IDs, ARM IDs, computed identifiers   | Exclude from variables.tf and tfvars               |
| location           | string     | Azure region/location                         | Exclude from variables.tf and tfvars               |
| password, secret, key, token, sas, connection_string, client_secret, private_key | string | Sensitive fields (credentials, secrets, tokens, keys, SAS, connection strings, client secrets, private keys) | Mark as sensitive in variables.tf (sensitive = true); exclude from tfvars; never commit values to source control |
| tags               | map(string)| Resource tags                                 | Add as a single map variable for all resources     |
| name               | string     | Resource name                                 | Include as variable, use Azure abbreviation naming |
| address_space      | list(string)| VNet address space                            | Include as variable, use abbreviation              |
| depends_on         | list       | Terraform dependency references               | Do not parameterize, keep as-is                    |
| jsonencode blocks  | object/map | Encoded property blocks (e.g., settings)      | Extract all fields inside as variables             |
| hardcoded literals | string/number/bool | Direct assignments in main.tf           | Convert to variables if not excluded by above rules|
| reference resources (network, monitoring, keyvault, etc.) | reference/data | External resources referenced in configuration | Always handle via Terraform data blocks, not as variables |

### Example: Handling jsonencode Blocks

```hcl
variable.tf

variable "settings_force_re_onboarding" {
	description = "Force re-onboarding setting."
	type        = bool
}

variable "settings_v_next_enabled" {
	description = "vNext enabled setting."
	type        = bool
}

main.tf
resource "azurerm_virtual_machine_extension" "example" {
	name                 = "example-vmext"
	settings             = jsonencode({
		forceReOnboarding = var.settings_force_re_onboarding
		vNextEnabled      = var.settings_v_next_enabled
	})
}
```
In this pattern, each field inside the jsonencode block is extracted as a separate variable and referenced using var.<variable_name>.

### Example: - [Golden Template] should define environment-agnostic tags:
```hcl
locals {
  golden_tags = {
    application     = "myapp"
    business_unit   = "finance"
    cost_center     = "CC-1234"
    owner           = "team-x"
    classification  = "internal"
  }
}

local.golden_tags["application"]
```

### Example: - [Hybrid Template] Keep tags inline in each resource as exported by aztfexport:
```hcl
resource "azurerm_storage_account" "example" {
  # ...
  tags = {
    environment = "prod"
    owner       = "team-x"
  }
}
```
These tags never change across environments.

### Example: - DO NOT parameterize location unless you want to recreate everything
Location stays inline:
```hcl
location = "eastus2"
```
### Example:- Handeling Sensitive Fields (Credentials, Secret, tokens, Keys, SAS, Connection string, Client Secret, Private Key etc.)

In variables.tf:

```hcl
    variable "db_password" {
      type      = string
      sensitive = true
    }

    variable "client_secret" {
      type      = string
      sensitive = true
    }

    variable "storage_sas" {
      type      = string
      sensitive = true
    }
```
 This ensures:
- Terraform masks them in logs
- They never appear in plan output
- They cannot be accidentally printed

### NEVER put sensitive values in tfvars
Do not do this:
```hcl
db_password = "SuperSecret123!"
```
Instead, use one of these safe sources:
- Terraform Cloud workspace variables
- GitHub Actions encrypted secrets
- Key Vault data sources

### Replace with variable references:
```hcl
connection_string = var.storage_connection_string
```
- Use GitHub Action to store & Inject Sensitive Terraform Variables
  Or
- Use Terraform Cloud (TFC) is the cleanest and most secure option for deployments. (Best Practice)

 ## How to handle `depends_On`
 🛠️ Handling `depends_on` During Terraform Refactoring

Terraform’s dependency graph is powerful, and in most cases it automatically understands resource relationships. During refactoring—especially when cleaning up aztfexport‑generated code—you can safely remove many `depends_on` blocks.

This guide explains **when to remove**, **when to replace**, and **when to keep** `depends_on`.

### ✔ 1. Remove `depends_on` When Terraform Can Infer Dependencies
Terraform automatically infers dependencies when one resource references another.

#### Example
app_service_plan_id = azurerm_app_service_plan.plan.id
This reference already creates a dependency. You do not need:
```hcl
depends_on = [azurerm_app_service_plan.plan]
```

### ✔ 2. Replace Resource References With Data Sources for External Infrastructure
If the referenced resource is not managed by your module, remove the `depends_on` and use a data source instead.

### Wrong
```hcl
depends_on = [azurerm_virtual_network.vnet]
```
### Correct
```hcl
data "azurerm_virtual_network" "vnet" {
  name                = "vnet-hub-prod"
  resource_group_name = "rg-network-prod"
}
```
Then reference it normally:
subnet_id = data.azurerm_subnet.app_subnet.id

### ✔ 3. Keep `depends_on` Only for Non‑Inferable Dependencies
There are a few cases where Terraform cannot determine the correct order.

  ### Case A — Diagnostic Settings
  ```hcl
  depends_on = [azurerm_app_service.app]
  ```
  ### Case B — Role Assignments
  ```hcl
  depends_on = [azuread_service_principal.sp]
  ```
  ### Case C — Private Endpoints
  ```hcl
  depends_on = [azurerm_private_dns_zone_virtual_network_link.link]
  ```
  ### Case D — Key Vault Access Policies
  ```hcl
  depends_on = [azurerm_key_vault.kv]
```
### Summary — How to Handle aztfexport `depends_on`
  - Remove when Terraform can infer dependencies.
  - Replace external infra references with data sources.
  - Keep only for special cases where Terraform cannot infer ordering.

### Terraform `.tfvars` Standards — Complete Table

| **Category** | **Standard / Rule** | **Explanation** |
|--------------|----------------------|------------------|
| **Naming** | `terraform.tfvars` | Auto‑loaded default variable file. |
| | `*.auto.tfvars` | Auto‑loaded environment or module‑specific files. |
| | `dev.tfvars`, `test.tfvars`, `prod.tfvars` | Must be loaded explicitly using `-var-file`. |
| | Store env files under `environments/<env>/terraform.tfvars` | Clean separation for Dev/Test/Prod. |
| **Content Rules** | Only variable assignments | No resources, no modules, no locals, no logic. |
| | HCL format | Must follow HashiCorp Configuration Language syntax. |
| | No interpolation | No `${}` expressions inside tfvars. |
| **Sensitive Values** | **Never** store secrets in tfvars | Use Key Vault, Terraform Cloud, or pipeline secrets. |
| | Sensitive variables must be injected at runtime | Keeps repo clean and compliant. |
| **Environment Separation** | One tfvars file per environment | Dev/Test/Prod each get their own overrides. |
| | tfvars contain only environment‑specific values | Region, SKU, scaling, env tags, toggles. |
| | All shared/global values come from Golden Template defaults | Prevents duplication and drift. |
| **Promotion Workflow** | Same code, different tfvars | Golden Template version stays consistent. |
| | Dev → Test → Prod promotion | Enterprise standard for controlled rollout. |
| | Each stage loads its own tfvars | `-var-file=environments/dev/terraform.tfvars` |
| **Plan/Show Standards** | Must save plan to a file | `terraform plan -out=dev.plan` |
| | `terraform show` must read a plan file | `terraform show dev.plan` |
| | Each environment produces its own plan artifact | Enables approvals and auditability. |
| **Defaults vs Overrides** | Defaults belong in Golden Template | Application metadata, global tags, networking patterns. |
| | Overrides belong in environment tfvars | Region, SKU, scaling, env tags. |
| | Avoid duplication across tfvars | Move shared values to Golden Template. |
| **Validation** | Run `terraform validate` on every PR | Ensures syntax and variable correctness. |
| | Run `terraform plan` for each environment | Ensures no drift or unexpected changes. |
| **Folder Structure** | Use a clean environment folder layout | `environments/dev/terraform.tfvars` etc. |
| | Keep tfvars small and readable | Only override what differs. |

## STEP 4 Store Remote State in Terraform Cloud

To ensure collaboration, security, and reliability, store your Terraform state file remotely in Terraform Cloud instead of locally. This enables state locking, versioning, and team access.

### How to Configure Remote State with Terraform Cloud

1. **Add a backend block to your Terraform configuration (backend.tf):**

   ```hcl
   terraform {
     backend "remote" {
       organization = "<your-terraform-cloud-org>"

       workspaces {
         name = "<your-workspace-name>"
       }
     }
   }
   ```

   - Replace `<your-terraform-cloud-org>` with your Terraform Cloud organization name.
   - Replace `<your-workspace-name>` with the workspace name you want to use for this environment.

**Benefits:**
- Centralized, secure state management
- State locking to prevent concurrent changes
- Version history and auditability
- Easy collaboration for teams


## STEP 5 RUN terraform init, validate & plan

### Command Sequence to Execute Terraform (Recommended)

1. **Initialize Terraform (required for remote or local state):**
  ```sh
  terraform init
  ```
  > This will prompt for authentication if using Terraform Cloud.

2. **Validate the configuration:**
  ```sh
  terraform validate
  ```

3. **(Optional) Format the code for consistency:**
  ```sh
  terraform fmt
  ```

4. **Generate and review the plan:**
  ```sh
  terraform plan -var-file=environments/<env>/terraform.tfvars -out=<env>.plan
  terraform show <env>.plan
  ```
  Replace `<env>` with your environment (dev, test, prod, etc).

# Terraform Variable Naming Convention

## Purpose
This guideline defines a concise, consistent, and unique variable naming convention for Terraform variables generated for Azure resources, optimized for names 25–30 characters long.

## Naming Pattern

```
<resource_abbr>_<resourc_instance>_<prop_abbr>
```

- **resource_abbr**: Short, standard abbreviation for the Azure resource type
- **idx**: Resource index or instance number (e.g., 0, 1, 2)
- **prop_abbr**: Short abbreviation for the property/attribute

### Examples
| Full Variable Name                                               | Shortened Name      |
|-----------------------------------------------------------------|---------------------|
| azurerm_linux_virtual_machine_res_3_name                        | azvm_3_name         |
| azurerm_dev_test_global_vm_shutdown_schedule_res_4_timezone     | dtvmss_4_tz         |
| azurerm_virtual_network_res_21_address_space                    | vnet_21_addr        |
| azurerm_resource_group_res_1_name                               | rg_1_name           |
| azurerm_availability_set_res_2_platform_fault_domain_count      | aset_2_pfdc         |
